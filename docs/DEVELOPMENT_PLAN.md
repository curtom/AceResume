# AceResume 整体开发计划（待评审）

> 文档状态：草案，等待项目负责人评审  
> 规划范围：V1.0 MVP 及 V1.1 候选项  
> 编写依据：`docs/PRD.md`、`docs/TECHNICAL_ARCHITECTURE.md`、`docs/CODING_STANDARDS.md`、`AGENTS.md`  
> 当前仓库状态：已具备需求文档、技术文档、编码规范和静态交互原型；正式 pnpm Monorepo 尚未初始化  
> 执行约束：本计划获明确批准前，不开始工程初始化或业务功能开发

## 1. 计划目的

本计划把已确认的产品需求和技术架构拆分为可顺序验收的研发阶段，确保：

- 先完成结构化编辑、可信内容和稳定导出三条 MVP 主线。
- 保持前后端分离、pnpm Monorepo、NestJS 模块化单体、独立 Worker 的既定架构。
- 先建立 Schema、权限、失败路径和测试门禁，再扩展模板、文档解析和 AI 能力。
- AI 仅产生有来源、待确认的建议，不能绕过用户批准直接修改正式简历。
- 每个阶段都有明确输入、任务清单、交付物和退出条件；未通过阶段门禁不进入下一阶段。
- V1.0 的 P0 需求与 V1.1/P2 候选项分离，避免范围膨胀。

## 2. 规划基线与范围边界

### 2.1 V1.0 必须交付

- 邮箱注册、验证、登录、找回密码、会话续期和退出。
- 结构化个人资料库与多简历管理。
- 模块化编辑、基础富文本、排序、显隐、受控样式、撤销/重做。
- 自动保存、IndexedDB 临时草稿、乐观锁和最近 20 个关键版本。
- 8～12 套公共模板、A4 分页预览和文本可选择的 PDF 导出。
- DOCX、文本型 PDF、TXT、Markdown 上传、解析、预览、旧简历候选识别和确认导入。
- 用户与所选材料范围内的 RAG 检索。
- 带来源、支持状态、风险标记和修改前后差异的 AI 建议。
- 数字、关键实体、来源权限、来源冲突和提示注入校验。
- 模板、模型、提示词、用户状态、运行监控和审计日志的基础管理后台。
- 不同用户之间的资源隔离，以及文档、AI、导出、删除任务的幂等和失败恢复。

### 2.2 V1.0 明确不做

- 手机端完整编辑体验。
- Canva 式自由画布、绝对定位或任意元素拖拽。
- 扫描件、图片简历 OCR。
- 任意 Word/PDF 版式一键复刻。
- 用户模板社区、模板交易、订阅、支付。
- 多人协作编辑。
- 自动投递、招聘网站账号连接、职位爬取。
- GraphQL、WebSocket、Python 服务、独立向量数据库、微服务和 Kubernetes。
- 在普通受控 TypeScript 工作流足够时提前引入 LangGraph.js。
- 模型微调。

### 2.3 现有静态原型的使用边界

- `static-demo/` 只作为视觉方向和交互讨论材料，不作为生产代码直接迁移。
- 当前工作台、简历编辑器和 AI 抽屉可用于确认布局与交互意图。
- “我的简历、个人资料、材料库、模板中心、账号设置”目前主要是占位展示，不能视为需求已实现。
- 静态原型中的“投递市场”不属于已确认 PRD 信息架构；V1.0 不实施该入口。
- 静态原型使用浏览器打印模拟导出，正式实现必须改为共享模板引擎与服务端 Playwright/Chromium PDF。
- 静态原型中的前端假数据、延时和直接写入行为不得带入正式 AI、保存或导入流程。

## 3. 阶段总览与依赖

技术架构第 26 节定义的七个研发阶段保持不变；本计划在其前后增加两个质量门禁阶段。

| 1 | 工程骨架 | 可独立启动的 Web、API、Worker 与本地基础设施 | 阶段 0 |

| 3 | 简历编辑核心 | 多简历、结构化编辑、保存与版本闭环 | 阶段 2 |
| 4 | 模板、预览与导出 | 8～12 套模板及预览/PDF 一致性 | 阶段 3 |
| 5 | 材料库与旧简历导入 | 文件上传、解析、确认导入和一致删除 | 阶段 1、2、3 |

## 4. 全阶段共同规则

### 4.1 需求与架构

- 开始每项功能前，定位对应 PRD 编号、业务流程、异常场景和验收标准。
- 如果 PRD、技术架构、编码规范和现有实现冲突，停止该项实现，先记录冲突并确认边界。
- 架构级新决策写入 `docs/adr/`，不得只存在于代码或聊天记录中。
- 不为未进入当前阶段的功能创建复杂抽象、空目录或重复框架。

### 4.2 契约与数据

- API、简历、模板、任务、SSE 和 AI 输出均以 Zod Schema 为单一事实来源。
- API 前缀为 `/api/v1`；JSON 使用 `camelCase`；数据库使用 `snake_case`；时间使用 UTC ISO 8601。
- 请求和响应类型来自 `packages/contracts` 或 OpenAPI 生成客户端，页面组件不得猜测接口字段。
- JSONB 必须受 Schema 约束并带有或关联 `schema_version`。
- 所有业务列表分页；并发敏感更新使用版本号；异步创建使用幂等键。

### 4.3 安全与隐私

- 所有用户资源在服务端按所有权过滤，不依赖前端隐藏按钮。
- Access Token 仅存前端内存；Refresh Token 使用 HttpOnly Cookie 并轮换，数据库只保存哈希。
- 密码使用 Argon2id。
- `.env`、Token、API Key、真实用户材料、数据库卷、日志和临时 PDF 不进入 Git。
- 日志不记录完整简历、文档正文、模型上下文、电话或邮箱。
- 外部数据统一按 `unknown` 接收并经运行时 Schema 校验。
- 富文本和解析文本展示前清理，链接使用协议白名单。

### 4.4 异步任务

- 文档解析、Embedding、AI、PDF、邮件和存储清理通过 BullMQ 执行。
- API 对长任务返回任务 ID，不阻塞 HTTP 请求。
- 任务携带 `jobId`、`userId`、业务对象 ID 和幂等键；执行前重新检查对象与权限。
- 默认最多重试 3 次并指数退避；参数错误等不可重试错误直接失败。
- SSE 只负责进度通知；断线后通过任务查询恢复，不影响后台任务。

### 4.5 每项功能的 Definition of Done

- 满足当前阶段内对应 PRD 范围和验收点。
- 请求、响应和外部输入已通过共享 Schema 校验。
- loading、empty、error、success、权限、并发和可恢复失败路径已处理。
- 新增或修改的 API 已同步 OpenAPI。
- 相关单元、组件、集成或 E2E 测试已补充。
- `pnpm lint`、`pnpm typecheck`、`pnpm test`、`pnpm build` 全部通过。
- 适用的数据库迁移、水平越权、Worker 幂等、视觉回归或 AI 评测通过。
- Git diff 无无关格式化、临时文件、敏感数据或用户已有修改丢失。

## 16. 风险控制与决策点

| 风险 | 最晚决策点 | 控制措施 |
|---|---|---|
| PDF 与预览不一致 | 阶段 0 | 先做单栏技术验证，共用模板引擎，固定字体与视觉基准 |
| AI 捏造或越权引用 | 阶段 6 开始前 | Schema、来源权限、确定性数字/实体校验、用户确认和评测集 |
| 编辑器范围膨胀 | 阶段 0 原型评审 | 只做结构化模块和模板允许的样式参数，不做自由画布 |
| 文件解析不稳定 | 阶段 0/5 | 明确格式和失败类型，Worker 隔离、资源限制、可重试 |
| 删除不一致 | 阶段 0/5 | 幂等清理任务、状态记录、停止未执行任务、删除后召回测试 |
| 自动保存覆盖数据 | 阶段 3 | IndexedDB + `baseVersion` + 409 冲突交互，不使用最后写入覆盖 |
| 模板升级破坏历史 | 阶段 4 | 模板版本化，简历/导出绑定明确模板版本 |
| AI/基础设施不可用 | 阶段 1 起 | 适配器、Mock Provider、明确错误、保证手动主链路独立 |
| 单人开发任务过载 | 每阶段评审 | 阶段门禁、P0 优先、最小完整改动、P1 延后、避免过早抽象 |

## 17. 评审与启动规则

### 17.1 本轮评审建议重点

- 阶段划分和依赖顺序是否符合预期。
- V1.0/P1/P2 的范围是否需要调整。
- 静态原型中哪些视觉与交互必须保留。
- 阶段 0 的技术验证项是否完整。
- 每个阶段的退出条件是否足以进入下一阶段。
- 是否接受“投递市场不进入 V1.0”的边界。

### 17.2 启动条件

在项目负责人明确回复批准本计划或给出修订意见前：

- 不初始化 Monorepo。
- 不新增依赖。
- 不创建数据库迁移。
- 不修改静态原型或开发业务功能。

批准后从阶段 0 开始，先提交该阶段的细化工作项和待确认问题；每个阶段结束时提供完成内容、验证结果、Git diff 范围和剩余限制，获得确认后再进入下一阶段。
